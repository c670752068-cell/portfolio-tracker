## 2. 本轮三个问题与根因（已核实，直接采信）

### 问题 A（高）：量化系统的**模块级观察期开关被完全忽略**

`types.ts:215-218`：
```ts
export interface QuantSellSnapshot {
  shadow: boolean;                      // ← 整个卖出模块是否处于观察期
  symbols: Record<string, QuantSellFamily>;
}
```

全仓检索 `sell.shadow` / `sell?.shadow` 的读取点：**零命中**。

也就是说：量化系统若把整个卖出模块标记为"观察期、未正式生效"（测试夹具 `quantAnalysis.ts:135` 就是 `shadow: true`），网站**照样把每个族显示成「卖出窗口开启」**。`sellStatus.ts` 只读了单条信号的 `evidence.shadow`，漏了模块级开关。

> 这直接对应用户的疑问「怎么有这么多需要卖」——一批本应是"观察期"的信号被呈现成了可执行动作。

**修法**：`sellStatus.ts` 的 `resolveSellStatus`：当 `snapshot.sell.shadow === true` 时，**任何**命中结果一律降级为 `state: 'observation'`（即使 `evidence.shadow === false`）。模块级为真时不得出现 `window_open`。UI 文案沿用现有「观察期」样式，并在卖出窗口标题旁加一行：`量化卖出模块当前为观察期，全部信号均未正式生效`。

**测试**：模块 `shadow: true` + 单条 `shadow: false` → 结果必须是 `observation`；模块 `shadow: false` + 单条 `shadow: false` → `window_open`（防回归）。

### 问题 B（高）：止盈剧本可能张冠李戴，且用户无从分辨

**B1 — 族匹配没有把"精确匹配"排在前面。** 两处同样写法：

`ConditionLookup.tsx:401`
```ts
Object.values(snapshot.sell.symbols).find(
  (item) => item.family === selectedSellSymbol || item.held_symbols.includes(selectedSellSymbol))
```
`sellStatus.ts` 同款 OR 写法。

`.find()` 取的是 `Object.values()` 顺序里的**第一个**命中。当一个代码既是某个族的名字、又出现在另一个族的 `held_symbols` 里时，**谁排前面谁赢** —— 结果可能是拿着 A 族的名字，显示了 B 族的止盈剧本。

**修法**：改为两趟匹配，**精确 family 匹配优先**，找不到再退回 `held_symbols` 包含匹配；若 `held_symbols` 匹配到**多个**族，取市值最大的一个并在 UI 标注「该标的同时属于多个族，已按市值最大者展示」。两处逻辑统一抽到 `sellStatus.ts` 导出同一个 `findSellFamily(snapshot, symbol)`，`ConditionLookup.tsx` 改为调用它（消除两份重复实现）。

**B2 — 剧本类型标签存在但从不显示。** `types.ts:204` 有 `playbook.label?: string`（夹具值为 `'个股'`），`ConditionLookup.tsx` 只用了 `sell_steps`、`available`、`risk_first_order`，**`label` 从未渲染**。

用户反馈「FNGU 这种三倍的应该是 50% 才卖」，而界面上显示的是 `盈利 5%–7% 减 2%` 这类档位。**在标签不可见的情况下，无法判断这是"网站取错了剧本"还是"量化侧给 FNGU 配的就是这份剧本"。**

**修法**：止盈阶梯卡片标题旁显示 `剧本：{playbook.label}`（无 label 时显示"未标注"）。同时把该族的 `family`、`held_symbols`、`playbook.label` 一并加入 V10 已有的「原始判定数据」折叠块（若尚未包含）。

> **注意**：`sell_steps` 的数值来自量化系统，网站**不得修改、不得过滤、不得自设 50% 阈值**。本 Phase 的目的是让"到底用了哪份剧本"可见，从而定责。用户所说的 50%，可能指"涨 50% 才开始卖"，也可能对应夹具里 `contentment.minimum_reduction_pct: 50`（建议至少减仓 50%）—— **两种含义不同，禁止猜测后自行实现**，先把标签和原始数据显示出来，由用户与量化侧确认。

**测试**：族名精确匹配优先于 held_symbols 包含匹配（构造一个"X 既是 X 族名、又在 Y 族 held_symbols 里"的快照，断言返回 X 族）；`playbook.label` 渲染到界面；无 label 时显示"未标注"。

### 问题 C（中）：成本读不出来，但界面从不告诉用户"缺什么、怎么补"

现状（已核实）：
- 量化系统的 `positions-status` 载荷**根本没有成本字段**（只有 broker / symbol / asset_type / qty / market_value）；
- 正股成本来自另一个映射 `snapshot.holding_costs[symbol]`，且只有 `coverage === 'complete' && auto_fill_allowed` 时才会自动填入（`quantSync.ts:163-176`）；
- **期权成本量化侧完全没有**（V11 已确立：绝不能拿正股每股成本顶替），只能靠「补充期权详情」截图导入；
- 目前只有卖出窗口里按族显示 `unknownCostHoldings`，**全局没有任何一处告诉用户：哪些持仓缺成本、原因是什么、该做什么**。

**修法**（纯展示，不改任何成本计算）：

1. 新纯函数 `src/costCoverage.ts`：
   ```ts
   export type CostGapReason = 'option_no_source' | 'quant_coverage_incomplete' | 'manual_missing';
   export interface CostGapRow { symbol: string; assetType: string; broker?: string; reason: CostGapReason; }
   export function analyzeCostCoverage(holdings, holdingCosts): {
     total: number; costed: number; gaps: CostGapRow[];
   }
   ```
   判定：期权且自身无 `buyPrice/costOverride` → `option_no_source`；非期权且 `holdingCosts[symbol]` 缺失或 `coverage !== 'complete'` 或 `auto_fill_allowed === false` → `quant_coverage_incomplete`；其余无成本 → `manual_missing`。
2. 「设置」页（或持仓页顶部，择一，不新增 Tab）新增「成本数据覆盖」小卡片：
   - 一行汇总：`已有成本 X / 共 Y 个持仓`；
   - 按原因分组列出缺失持仓，每组附一句可执行指引：
     - `option_no_source` → 「期权成本量化系统未提供，请在『持仓 → 补充期权详情』上传期权详情页截图」
     - `quant_coverage_incomplete` → 「量化系统对该标的的成本覆盖不完整（coverage=xxx），请在持仓表手动补填买入价，或联系量化侧确认该券商是否提供成本」
     - `manual_missing` → 「请在持仓表补填买入价」
3. **测试**：三种原因各一条持仓 → 分组正确、计数正确；全部有成本 → 卡片显示"全部持仓成本齐全"。

## 5. 需要用户确认 / 转给量化侧的两件事（网站侧不执行）

修完 Phase 2 后，界面会显示「剧本：xxx」和原始判定数据。请用户对照确认：

1. **FNGU 显示的剧本是哪一份？** 若显示的是「个股」剧本（5%/7%/10% 档位），而 FNGU 是三倍杠杆品种 → 属**量化侧剧本归类**问题，需向量化侧提需求："FNGU/TQQQ/SOXL 等三倍品种应套用三倍剧本，而非个股剧本"。
2. **用户所说的"50% 才卖"具体指什么？** 是"涨满 50% 才开始减仓"（属 `sell_steps` 阈值），还是"触发后至少减仓 50%"（属 `contentment.minimum_reduction_pct`）？两者是不同字段，确认后再决定是否需要量化侧调整配置。

另：**期权成本的根本解法**仍是向量化侧提需求 —— 在 `positions-status` 的每条 position 增加 `average_cost`（期权为每股权利金成本）或 `cost_basis`（该条持仓总成本）。属契约变更，须量化侧实现，网站侧不得自行改造。
