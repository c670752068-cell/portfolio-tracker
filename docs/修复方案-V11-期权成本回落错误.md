## 1. 根因（已用运行时实证确认，直接采信，不要重新排查）

### 现象
用户券商 App 显示 NVDA 未实现盈亏 **+21.98（+1.08%）**，网站「本族当前盈亏」显示 **浮亏 −60.20%**，止盈阶梯被误判为"尚未适用"。多个持仓族同时出错。

### 根因：期权行拿到了**正股的每股成本**，再乘以合约乘数 100

三段代码串起来构成这个 bug：

**① 量化系统的期权持仓，`symbol` 就是底层代码**（不是合约代码）。见契约 §3.2 与现有测试 `src/quantSync.test.ts:14`：
```ts
{ broker: 'futu', symbol: 'IGV', asset_type: 'option', qty: 2, market_value: 3_616 }
```
所以一条 NVDA 期权持仓，它的 `holding.symbol === 'NVDA'`，与正股完全同名。

**② 同步后期权的 `buyPrice` 是 0**（`src/quantSync.ts:90`）：
```ts
buyPrice: enhancement?.buyPrice ?? 0,
```
量化的 positions 载荷里**根本没有成本字段**（只有 broker/symbol/asset_type/qty/market_value），期权成本只能来自截图「补充期权详情」的增强数据；没做过增强就是 0。

**③ `familyPnl.ts:40-43` 的成本回落没有排除期权**：
```ts
const external = holdingCosts[normalize(holding.symbol)]?.weighted_average_cost;
if (typeof external === 'number' && ...) {
  return holding.shares * external * multiplier;   // multiplier = 100
}
```
`holdingCosts['NVDA'].weighted_average_cost` 是**正股每股成本**（约 203）。于是：
```
期权成本 = 合约张数 × 203 × 100
```
1 张合约就凭空产生约 **$20,300** 的成本。

**关键对照证据**：`src/quantSync.ts:163` 的 `applyQuantHoldingCosts` **明确排除了期权**：
```ts
if (holding.source !== 'quant-sync' || holding.assetType === 'option') return holding;
```
说明"正股每股成本不能给期权用"这条规则是已知的，只是 `familyPnl.ts` 这一处漏了同样的守卫。

### 运行时实证（诊断脚本已跑通并删除）
输入：NVDA 正股 10 股（buyPrice 203.15，市值 2053.7）+ NVDA 期权 1 张（buyPrice 0，市值 2000，乘数 100），`holdingCosts.NVDA.weighted_average_cost = 203.15`。
结果：`costBasis === 2031.5 + 20315` 断言**通过** —— 期权那 1 张合约独自贡献了 **$20,315** 成本。

### 影响面
用户持有 NVDA、MSFU、IGV、NKE 等多个标的的期权，**每一个含期权的持仓族都会被灌进一笔巨额假成本**，浮亏被系统性放大 —— 这就是"其他个股的价格也都错了"。市值一侧没有这个问题（`market_value` 由券商聚合直传）。

### 现有测试为何没抓到
`src/familyPnl.test.ts:24` 的期权用例给了 `buyPrice: 2`（期权自身成本已知），走的是 `familyPnl.ts:37` 那条分支，**从未覆盖 buyPrice 为 0 而回落到 holdingCosts 的路径**。

## 2. 任务

### Phase 1：修复成本回落（核心，测试先行）

1. **先写失败测试**（`src/familyPnl.test.ts` 新增），断言正确行为：
   - 用例 A：期权行 `assetType: 'option'`、`symbol: 'NVDA'`、`buyPrice: 0`、`option.contractMultiplier: 100`，`holdingCosts.NVDA.weighted_average_cost = 203.15` → **该期权不计入 costBasis**；正股照常计入；`coverage === 'partial'`；`pnlPct` 只反映正股部分。
   - 用例 B：期权行**自身** `buyPrice > 0`（来自「补充期权详情」增强）→ 照常按 `shares × buyPrice × multiplier` 计入，`coverage === 'complete'`（保持 `familyPnl.test.ts:24` 现有行为不回归）。
   - 用例 C：期权行有 `costOverride > 0` → 优先用 costOverride。
   - **先运行，确认用例 A 失败**（会得到多出来的 20315），把失败输出贴进报告。
2. 改 `familyPnl.ts` 的 `costBasisFor`：`holdingCosts` 回落分支**仅对非期权持仓生效**。与 `quantSync.ts:163` 保持同一条规则。期权在没有自身成本时，成本视为未知（返回 null）。
3. 不改 `costOverride` 和 `buyPrice` 两条既有优先级。

提交：`fix: never derive option cost from underlying share cost`

### Phase 2：成本不完整时的展示必须诚实（防止修完仍误导）

修复后，含期权的族会变成 `coverage: 'partial'`（期权成本未知）。此时：

1. 「本族当前盈亏」卡片必须显示：
   - 百分比后缀标注 **「仅含已知成本部分」**；
   - 一行说明：`N 个持仓成本未知（期权成本需用「补充期权详情」导入），未计入本次盈亏`，并列出这些持仓的代码；
   - `coverage === 'unavailable'` 时不显示任何百分比，只显示市值与「成本未知」。
2. **浮亏闸门收紧**：V10 Phase 3 的"浮亏时置灰止盈阶梯并提示尚未适用"，仅在 `coverage === 'complete'` 时按原样生效；`coverage === 'partial'` 时提示语改为：
   > 已知成本部分为浮亏 −X%（另有 N 个持仓成本未知）。止盈阶梯参考请以券商实际成本为准。
   —— 不得用不完整数据下"尚未适用"的断言口吻。
3. 测试：partial 场景出现「仅含已知成本部分」与未知持仓清单；unavailable 场景不显示百分比；complete 场景与 V10 行为一致。

提交：`fix: qualify family pnl when cost coverage is incomplete`

## 4. 后续可选（本轮不做，供用户决定）

期权成本目前只能靠截图补充。若希望彻底自动化，需向**量化侧**提需求：在 `positions-status` 的每条 position 上增加 `average_cost`（期权为每股权利金成本）或 `cost_basis`（该条持仓总成本）字段。这属于契约变更，须由量化侧实现，网站侧不得自行改造。
